# Code Review — Ревью кода с мульти-агентной валидацией

Ревью: $ARGUMENTS

## Контекст

Если `$ARGUMENTS` содержит PR номер или URL → ревью PR.
Если пустой → ревью текущих изменений (staged + unstaged).
Если содержит путь к файлу → ревью конкретного файла.

## Процесс

### Шаг 1: Предварительная проверка (haiku agent)

Если PR:
- PR закрыт → пропустить
- PR — draft → пропустить
- PR тривиальный (автогенерация, только lockfile) → пропустить
- Claude уже оставил ревью → пропустить

Если локальные изменения:
- Нет изменений → сообщить и остановиться

### Шаг 2: Сбор контекста (параллельные haiku agents)

Agent A: Собрать CLAUDE.md файлы
- Корневой CLAUDE.md
- CLAUDE.md в директориях изменённых файлов
- Project MEMORY.md

Agent B: Суммаризация изменений
- Какие файлы изменены, что именно
- Контекст из PR description (если есть)

### Шаг 3: Ревью (4 параллельных агента)

**Agent 1 + 2 (sonnet)**: CLAUDE.md compliance
- Проверить изменения на соответствие правилам из CLAUDE.md
- Для каждого нарушения: процитировать конкретное правило

**Agent 3 (opus)**: Баги и логические ошибки
- Только в изменённом коде (не pre-existing issues)
- Syntax errors, type errors, missing imports
- Логические ошибки, которые дадут неверный результат
- Security: SQL injection, XSS, CORS, hardcoded secrets

**Agent 4 (opus)**: Контекстный анализ
- git blame для понимания истории
- Проверка консистентности с остальным кодом
- Security baseline: CORS config, rate limiting, headers, input validation

### Шаг 4: Валидация (параллельные agents per issue)

Для КАЖДОГО найденного issue → отдельный agent проверяет:
- Это реальная проблема или false positive?
- Код действительно нарушает указанное правило?
- Баг действительно приведёт к ошибке?

### Шаг 5: Фильтрация

Оставить ТОЛЬКО валидированные issues.

**НЕ флагать (false positives)**:
- Pre-existing issues (были до этого PR)
- Код, который выглядит как баг, но корректен
- Педантичные замечания, которые senior инженер не отметит
- Issues, которые поймает линтер
- Общее качество кода (если не нарушает CLAUDE.md)
- Issues с lint-ignore комментариями

**Флагать ТОЛЬКО HIGH SIGNAL**:
- Код, который не скомпилируется (syntax, types, imports)
- Код, который точно даст неверный результат
- Чёткие нарушения CLAUDE.md с цитатой правила
- Security vulnerabilities (injection, XSS, exposed secrets)

### Шаг 6: Отчёт

Формат вывода в терминал:

```
## Code Review

Найдено [N] issues:

1. [Описание проблемы] (причина: bug/CLAUDE.md/security)

   [ссылка на файл:строка]

2. [Описание проблемы]

   [ссылка на файл:строка]
```

Если issues НЕ найдены:
```
## Code Review

No issues found. Checked for bugs, security, and CLAUDE.md compliance.
```

Если указан `--comment` → опубликовать как комментарий к PR через `gh pr comment`.

## Правила

1. Создай TodoWrite список перед началом
2. Используй `gh` CLI для GitHub (НЕ web fetch)
3. Ссылки на код: `https://github.com/owner/repo/blob/[full-sha]/path/file#L[start]-L[end]`
4. Один комментарий = один уникальный issue (без дублей)
5. Для маленьких фиксов — предлагай конкретный код
6. Для больших (6+ строк, структурные) — описывай подход
